How to submit a future candidate — only after the gate passes

The steps below document the organizer's upload workflow and byte checks for a future, independently promoted candidate. No file linked on this site is currently recommended for upload. Steps 1–2 check potential range and nodata failures before a future candidate is sent. The original rejected bytes are unavailable, so the earlier "Predicted values must be in range [0, 1]" message has not been root-caused.

  1. Do not use any currently linked research artifact for submission. If a genuinely new candidate passes the promotion gate, use only its exact, hash-identified output and its own validation receipt. Do not assume that an -allfinite suffix is appropriate.
  2. Verify the exact output against authenticated organizer inputs. Check one float32 band, EPSG:32611, 100 m pixels, exact training-data bounds, finite unmasked predictions in [0,1] inside those bounds, and null/NaN outside. The current local checker reads an owner-supplied mirror template, so even a passing local report is not proof of organizer acceptance. Retain the checked bytes, hashes, report, and portal receipt. The all-finite research variant here writes zeros outside; its NaN sibling follows a mirrored sample convention but fails a NaN-intolerant raw comparison. Neither is a fix or an upload recommendation; the original rejected TIFF bytes remain unavailable.
  3. Sign in to DrivenData and open competition 306. You must have joined the competition and, if it is a team competition, be a member of the team.
  4. Go to the “Submit” page — …/submit/.
  5. Upload the .tif file itself. Do not zip it. The portal reads the GeoTIFF directly.
  6. Only after a future candidate is promoted, fill the optional “Note” field with a concise, truthful method identifier and any required calibration context. Do not paste a note for either research-only artifact on this site. The H47-B research note records spacing 5 px / 500 m and nominal 6/7 (85.7 %) split-conformal coverage conditional on block exchangeability, with a clipped lower bound of 0.0; it is explicitly not a positive performance guarantee or an authorized portal note (see H47-B validation).
  7. If and only if the candidate passes the promotion gate and a slot is authorized, submit it through the portal. Record the timestamp, participant row, exact file hash, and organizer receipt separately. A public participant-level score must not be assigned to a TIFF without an authenticated score-to-file link.
  8. Verify current round rules and submission limits from the official competition page before any future upload. Do not assume that any round is unlimited, or use a possible limit exception to override the scientific promotion gate.
  9. If the portal rejects a future file, capture the exact message and preserve the exact rejected bytes plus the applicable instructions. The available sibling-file audit identifies a possible NaN failure mode, but does not establish the cause of the earlier rejection; see the irregularities log.

Metric algebra and the unresolved 0.2778 attribution

The forward identity is

1/DTI = α + α·(F/T) + β·(K/T),    α = 0.2, β = 0.8
x = T/K,  ρ = F/K  ⇒  x = (αρ + β)/(1/DTI − α)

ρ = F/K is not the same ratio as F/T. At an illustrative F/K = 8.02—whose provenance as an observed participant ratio is unverified—DTI 0.3195 requires 82.05 % weighted recall, not 102.7 % or an impossible value. The alternate F/T = 8 scenario requires about 60.16 % weighted recall for the same target. Full corrected tables and forward-equation regression checks are on the evidence page.

  • Masking: official DrivenData staff says known USGS/INGENIOUS pixels are excluded from evaluation and do not count toward penalty terms. Deleting predictions exactly on those masked pixels therefore cannot improve DTI. Any effect of pruning nearby, evaluated pixels requires a controlled ablation on the unmasked evaluation domain.
  • H33-2-B2: the public 0.2778 row is participant-level and is not authenticated to this TIFF; its owner page marks the raster unscored. Artifact counts and covered-kernel integrals are descriptive only and cannot explain a public score without a verified file/score link.
  • Marginal rule: for a single new dot with credit dT = k and false-positive increment dF = 1 − k, it improves DTI iff k > α·DTI. This local rule does not prove that a broader pruning or emission strategy improves a held-out score.

Limitations you should weigh before trusting anything here

  • No GEMSDOE47 candidate has an authenticated DrivenData score. Public participant-level scores exist, but the project lacks organizer receipts linking them to the TIFFs. F1–F5 are local model outputs, not private leaderboard scores.
  • The LATI fit uses a small, dependent observation set. Twelve owner-reported raster/score pairs are available; the alleged H33-2-B2 / 0.2778 pair is contested and is only a conditional scenario. Several maps are nested thinnings, so the effective sample size is smaller still.
  • The H33-to-0.2778 attribution is unresolved. A coarse sensitivity grid has positive LOO improvement at assumed scores through 0.2200 and negative improvement by 0.2400; this is not an exact break-even, causal ablation, or verdict. The public board does not identify the TIFF.
  • Some H47-GSA cross-fit metrics include that contested association and require a sensitivity rerun without H33. Against the d2.8 reference it underperforms on four local frames; the F2 win is against its own in-fold fitted objective and is not independent. The submission gate remains closed pending new, adequately validated evidence.
  • Optimizer’s curse is large in the in-fold fits (reported gap ≈0.30 DTI). Treat all in-fold gains as exploratory, not as independent performance evidence.
